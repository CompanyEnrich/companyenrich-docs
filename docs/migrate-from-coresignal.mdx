This guide is for engineers whose code, scripts, or AI agents call the Coresignal API and are moving some or all of those calls to the CompanyEnrich V2 API. It maps each Coresignal endpoint, lists the behavior that changes in your code, and shows how to check the result on records you already have before you switch traffic.

<Note>
  Coresignal behavior on these pages was checked against Coresignal's public documentation and OpenAPI specification on November 25, 2026. The mapping covers the Multi-source Company and Employee APIs, the Contact Enrichment API, and Bulk Collect. Base and Clean endpoints map to the same CompanyEnrich endpoints, but their record fields are not covered. CompanyEnrich behavior comes from the [V2 API reference](/api-reference/v2/overview). The full mapping is also available as JSON at [/migrations/coresignal.json](https://docs.companyenrich.com/migrations/coresignal.json).
</Note>

## Switch company enrichment in five minutes

This is the shortest path: one enrichment call by website, moved to the V2 API with the Python SDK.

<Steps>
  <Step title="Get an API key">
    Create a key at [app.companyenrich.com/access-keys](https://app.companyenrich.com/access-keys) and export it as `COMPANYENRICH_API_KEY`. Check it with [`GET /v2/me`](/api-reference/v2/get-me), which is free:

    ```bash
    curl https://api.companyenrich.com/v2/me \
      -H "Authorization: Bearer $COMPANYENRICH_API_KEY"
    ```
  </Step>
  <Step title="Install the SDK">
    ```bash
    pip install companyenrich
    ```

    The [Python SDK](/docs/python-sdk) needs Python 3.10 or later. There are also SDKs for [JavaScript](/docs/javascript-typescript-sdk), [Ruby](/docs/ruby-sdk), and [PHP](/docs/php-sdk), and a [CLI](/docs/cli).
  </Step>
  <Step title="Replace the call">
    <CodeGroup>

    ```python Before (Coresignal)
    import os

    import requests

    response = requests.get(
        "https://api.coresignal.com/cdapi/v2/company_multi_source/enrich",
        headers={"apikey": os.environ["CORESIGNAL_API_KEY"]},
        params={"website": "stripe.com"},
    )
    if response.status_code == 404:
        company = None
    else:
        response.raise_for_status()
        company = response.json()
        print(company["company_name"], company["employees_count"], company["hq_country_iso2"])
    ```

    ```python After (CompanyEnrich)
    from companyenrich import CompanyEnrich, NotFoundError

    client = CompanyEnrich()  # reads COMPANYENRICH_API_KEY

    try:
        company = client.companies.enrich("stripe.com")
        country = (company.get("location") or {}).get("country") or {}
        print(company.get("name"), company.get("employees"), country.get("code"))
    except NotFoundError:
        company = None  # no match, not charged
    ```

    ```bash cURL
    curl "https://api.companyenrich.com/v2/companies/enrich?domain=stripe.com" \
      -H "Authorization: Bearer $COMPANYENRICH_API_KEY"
    ```

    </CodeGroup>

    Send a bare domain, such as `stripe.com`. Coresignal also accepts full URLs, so strip the scheme, `www.`, and any path from the values you pass.
  </Step>
  <Step title="Update the fields you read">
    | Coresignal field | CompanyEnrich field | Change |
    | --- | --- | --- |
    | `company_name` | `name` | Renamed |
    | `website_domain` | `domain` | Renamed |
    | `founded_year` | `foundedYear` | An integer instead of a string |
    | `employees_count` | `employees`, or `workforce.observedEmployeeCount` with `expand=workforce` | A range such as `1K-5K`, or a count with the expansion |
    | `hq_country_iso2` | `location.country.code` | Renamed, same ISO code |
    | `professional_network_url` or `linkedin_url` | `socials.linkedinUrl` | Renamed |

    The [field mapping](/docs/migrate-from-coresignal-field-mapping) covers every other field.
  </Step>
  <Step title="Keep your not-found handling">
    Both APIs return `404` when there is no match, and neither charges for it. The SDK raises `NotFoundError`.
  </Step>
</Steps>

## What takes longer

| Workload | Why | Guide |
| --- | --- | --- |
| Search, then collect | Coresignal search returns IDs, and you collect each record. CompanyEnrich search returns full records, up to 100 per page, and charges per result. | [Search, then collect](#search-then-collect) |
| Search queries | An Elasticsearch `bool` query becomes a flat `filter` in which every filter must match, with no OR across fields and no sorting. | [Search queries](/docs/migrate-from-coresignal-search) |
| Stored records | Coresignal IDs do not carry over, and value labels change, such as `51-200 employees` to `51-200` and `C-Level` to `c-suite`. | [Field mapping](/docs/migrate-from-coresignal-field-mapping) |
| Bundles and fields | Coresignal returns the full record or the bundles you ask for. CompanyEnrich returns the base record and adds paid expansions. | [Field selection](#field-selection) |
| Person lookups | CompanyEnrich enriches a person by work email, not by profile URL or shorthand name. | [People](#people) |
| Contact data | CompanyEnrich finds work emails one person at a time, by CompanyEnrich person ID. | [People](#people) |
| AI agents and scripts | MCP tools change, and scripts that call the API with `curl` can use the CompanyEnrich CLI. | [Move your MCP setup](#move-your-mcp-setup) |

## Move your MCP setup

If your agent uses the Coresignal MCP server, add the CompanyEnrich server. The hosted server is at `https://mcp.companyenrich.com/mcp`. For example, in Claude Code:

```bash
claude mcp add --transport http companyenrich https://mcp.companyenrich.com/mcp
```

The [MCP server guide](/docs/mcp-server) covers Claude Desktop, Cursor, VS Code, and other clients, and lists the credits each tool uses. Then update any prompts or code that name Coresignal tools:

{/* generated: coresignal mcp */}

| Coresignal tool | CompanyEnrich tool | Notes |
| --- | --- | --- |
| `entity_search` | `search_companies` or `find_similar_companies` or `search_people` | Filters, a plain-language description, or 1 to 10 seed domains for lookalikes. Records come back in the response, with no separate preview or file step. Job searches have no equivalent. |
| `entity_fetch` | `enrich_company` or `enrich_company_by_properties` or `get_company_by_id` or `lookup_person_by_email` or `get_person_by_id` | A company by domain, name, social profile, or CompanyEnrich ID, and a person by work email or CompanyEnrich ID. No person lookup by profile URL, and no job records. |
| `email_enrich` | `enrich_person_email` | Work email for a CompanyEnrich person ID. |
| None | `get_company_workforce` | Headcount by department, with monthly history, for one company. |
| None | `get_current_user` | Credit balance. Free. |
| `entity_fields`, `artifact_read` | None | No field discovery or file reading. Records have the fixed fields in the company and person schemas, and results come back in each response. |

CompanyEnrich tools take plain values, such as a domain or a job title, and return records in the response, so your agent does not need a field discovery step or a file to read results from.

### Scripts that call Coresignal

Coresignal has no CLI, so scripts usually call the API with `curl`. The [CompanyEnrich CLI](/docs/cli) covers the same company and people workflows. Its search flags are named after the CompanyEnrich filters, so rewrite each clause as a flag, or send the full request body with `companyenrich api`.

| Coresignal request | CompanyEnrich CLI |
| --- | --- |
| `GET /v2/company_multi_source/enrich?website=stripe.com` | `companyenrich company enrich stripe.com` |
| `GET /v2/company_multi_source/enrich?social_url=...` | `companyenrich company enrich --linkedin-url "..."` |
| `POST /v2/company_multi_source/search/es_dsl` or `/search/filter` | `companyenrich company search` with flags such as `--country US` |
| Reading `x-total-results` | `companyenrich company count` with the same flags |
| `POST /v2/employee_multi_source/search/es_dsl` or `/search/filter` | `companyenrich people search` |
| `GET /enrichment/contacts?member_id=...` | `companyenrich people email <id>`, with a CompanyEnrich person ID |
| `POST /v2/data_requests/company_multi_source/es_dsl` | `companyenrich company export` with filter flags and `--limit` |
| Reading `x-credits-remaining` | `companyenrich me` |

A CompanyEnrich lookup that finds nothing exits with code 4. Handle that code in scripts that use `set -e`, or the script stops at the first unknown domain.

## Endpoint mapping

### Search, then collect

Most Coresignal integrations search first, which returns record IDs, then collect each ID, which returns the full record. CompanyEnrich search returns full records, so the two steps become one search call:

<CodeGroup>

```python Before (Coresignal)
import os

import requests

BASE = "https://api.coresignal.com/cdapi/v2/company_multi_source"
HEADERS = {"apikey": os.environ["CORESIGNAL_API_KEY"]}

query = {"query": {"bool": {"must": [{"match": {"hq_country_iso2": "US"}}, {"term": {"is_saas": True}}]}}}
ids = requests.post(f"{BASE}/search/es_dsl", headers=HEADERS, json=query).json()
for company_id in ids[:20]:
    company = requests.get(f"{BASE}/collect/{company_id}", headers=HEADERS).json()
    print(company["company_name"], company["website_domain"])
```

```python After (CompanyEnrich)
from companyenrich import CompanyEnrich

client = CompanyEnrich()  # reads COMPANYENRICH_API_KEY

page = client.companies.search(filter={"country": "US", "categories": "saas"}, page_size=20)
for company in page["items"]:
    print(company["name"], company["domain"])
```

</CodeGroup>

Treat the search and its collect calls as one call site when you migrate. Collect calls on IDs you stored earlier have no equivalent, because Coresignal IDs do not carry over: enrich those records by their stored domain instead.

### Supporting APIs

{/* generated: coresignal endpoints:supporting */}

| Coresignal | CompanyEnrich V2 | Notes |
| --- | --- | --- |
| `GET /v2/data_requests/{data_request_id}/files`, `GET /v2/data_requests/{data_request_id}/files/{file_name}` | [`GET /v2/batches/{id}`](/api-reference/v2/get-batches-id) | `data_request_id` → `id`. Drop `file_name`: each job has one results endpoint, with no files to name. Poll `GET /v2/batches/{id}` until the job completes, then download the results from the job's own endpoint, such as `GET /v2/companies/search/export/{id}/results`, as JSON, NDJSON, or CSV. There are no file names to list. List jobs with `GET /v2/batches` and cancel one with `POST /v2/batches/{id}/cancel`. |

## Request and response differences

### Authentication

| | Coresignal | CompanyEnrich |
| --- | --- | --- |
| Headers | `apikey: YOUR_CORESIGNAL_API_KEY` | `Authorization: Bearer YOUR_API_TOKEN` |
| Base URL | `https://api.coresignal.com/cdapi/v2/...`, and `https://api.coresignal.com/enrichment/contacts` for contact enrichment | `https://api.companyenrich.com/v2/...` |
| SDK | None. Calls use HTTP directly. | `CompanyEnrich()` reads `COMPANYENRICH_API_KEY`, or takes the key as its first argument |

### Response shape

| Call | Coresignal | CompanyEnrich |
| --- | --- | --- |
| Enrich and collect | The record is the body | The record is the body |
| Search | A JSON array of IDs, with the total in the `x-total-results` header and the next page in `x-next-page-after` | `items`, full records, and `nextCursor`. Get totals from the free count endpoint. |
| Search preview | An array of summaries, each with a `_score` | `items`, summaries without a score, and `total` |
| Bulk Collect | `request_id`, then a list of files to download | `id`, then [`GET /v2/batches/{id}`](/api-reference/v2/get-batches-id) and results as JSON, NDJSON, or CSV |
| Contact enrichment | `code`, `message`, and `data` with `email`, `email_status`, and `email_confidence` | `status`, `email`, and `certainty` at the top level |
| Errors | A `detail` message | A problem document with `type`, `title`, `status`, and `detail`. `422` adds `errors` per field. The `x-trace-id` header identifies the request. |

### Field names

Coresignal's documentation and its OpenAPI specification spell some fields differently. The documentation uses `professional_network_url`, `professional_network_shorthand_name`, `financial_website_url`, and `company_id`. The specification uses `linkedin_url`, `linkedin_shorthand_name`, `crunchbase_url`, and `id`. The [field mapping](/docs/migrate-from-coresignal-field-mapping) lists both spellings, so search your code for whichever it reads.

### Field selection

Coresignal returns the full record by default. `bundle` limits it to the core bundle plus the bundles you name, and `fields` narrows it further. CompanyEnrich always returns the base record. The company base record includes name, domain, description, industry, size and revenue ranges, location, and social profiles. Add `financial`, `keywords`, `naicsCodes`, `technologies`, or `workforce` with `expand`, and `company` or `education` on a person.

| Coresignal bundle | CompanyEnrich |
| --- | --- |
| `core_company_data` | The base record. Keywords and NAICS codes are the `keywords` and `naicsCodes` expansions. |
| `financial_information` | The `financial` expansion: funding rounds, stage, and stock symbol |
| `workforce_intelligence`, `growth_signals` | The `workforce` expansion, for department headcounts and the latest 12 months of history. [`GET /v2/companies/workforce`](/api-reference/v2/get-companies-workforce) pages through earlier months. |
| `company_intelligence` | The `technologies` expansion. Competitors, reviews, web traffic, news, and job postings have no equivalent. |
| `core_employee_data` | The base person record, with the `education` expansion for schools |
| `employer_information` | The `company` expansion, a company summary on each experience |
| `career_intelligence`, `social_influence` | No equivalent |

When you rewrite a call, turn its `bundle` and `fields` lists into an `expand` list that holds only the expansions your code reads. Each expansion adds credits.

### Matching

Neither API returns a confidence score for enrichment:

* Enrichment by domain looks up that domain. Coresignal also accepts full URLs, so normalize them to a bare domain first.
* Enrichment by a social profile URL requires the URL to match. If several companies match, CompanyEnrich returns the highest-ranked one.
* A person lookup by work email returns the person, or `404`. There is no lookup by profile URL.

### Status codes

| Status | Coresignal | CompanyEnrich |
| --- | --- | --- |
| `200` | A record, or a search that ran. Charged for collect and enrich. | A record, or a search that ran |
| `400` | Invalid request, including a `fields` value outside the selected bundles | Malformed request |
| `401` | Missing or invalid key | Missing or invalid key |
| `402` | Out of credits | Out of credits, or the plan does not include the request. Do not retry. |
| `403` | The service is not enabled for the key | The key may not perform this request |
| `404` | No record for the ID, URL, or website. Not charged. | No match. Not charged. |
| `409` | A duplicate Bulk Collect request | Not used |
| `422` | Invalid parameters, including an unknown Search Filters parameter | Validation failed. `errors` lists the messages per field. |
| `429` | Rate limit hit | Rate limit hit. Wait for the time the response gives. |
| `503` | A search that did not finish within 10 seconds, or a busy search service. Retry after `Retry-After`. | Server error |

The SDK raises a typed exception for each non-2xx status, such as `NotFoundError`, `PaymentRequiredError`, and `RateLimitError`.

### Billing behavior that affects your code

These differences change how you write retries, guards, and tests. Prices for each endpoint are in [Credits](/docs/credits).

* **No match is free on both APIs.** CompanyEnrich enrichment that finds nothing returns `404` and is not charged.
* **Search returns records, and is charged per result.** Coresignal search returns IDs at no cost. CompanyEnrich search returns full records, so there is no separate collect call, and an empty search costs one result's base price. Size a new query with the free [count endpoint](/api-reference/v2/post-companies-search-count) first.
* **Extra company fields are expansions.** Each one you request adds 1 credit per company returned, so request only the ones your code reads.
* **Work emails are a separate call.** [`GET /v2/people/{personId}/email`](/api-reference/v2/get-people-personid-email) costs 10 credits only when it finds an email your account has not accessed before.
* **Responses report their cost.** Read `x-credit-cost` and `x-credit-remaining` from the response headers, in place of `x-credits-remaining`.

### Pagination

| | Coresignal | CompanyEnrich |
| --- | --- | --- |
| Page size | `items_per_page`, up to 1,000 IDs | `pageSize`, 1 to 100 records |
| Next page | Send the `x-next-page-after` header value as `after` | Send the `nextCursor` from the last response as `cursor`, until it is omitted |
| Order | Last updated first by default, or by `id`, `_score`, or a numeric field | Relevance order |
| Cursor lifetime | None. `after` is a position in the sorted results. | 24 hours after the first page |

Coresignal `after` values do not work on CompanyEnrich, so restart any paging job from the first page. If your code needs a sorted list, fetch every page, then sort. The Python SDK pages for you with `search_all()`.

### Rate limits

Coresignal limits data requests per second by plan, and returns `503` when a search does not finish within 10 seconds. CompanyEnrich applies a global limit of 500 requests per minute per IP address and a per-route limit from your plan, reported in `x-ratelimit-limit`, `x-ratelimit-remaining`, and `x-ratelimit-window`. A batch of 50 domains is one request. The SDKs wait and retry on `429`. See [Rate limits](/docs/rate-limit).

### Values and URLs

| | Coresignal | CompanyEnrich |
| --- | --- | --- |
| Countries | Full names in `hq_country`, and ISO alpha-2 codes in `hq_country_iso2` | `code` (ISO 3166-1 alpha-2, such as `US`) and `name` |
| Company types | Labels such as `Privately Held` | Values such as `private` |
| Size ranges | `51-200 employees`, with some ranges written several ways | `1-10` through `over-10K` |
| Seniority and department | Labels such as `C-Level` and `Engineering and Technical` | Values such as `c-suite` and `engineering-technical` |
| Headcount | A count, `employees_count` | A range, `employees`, or a count with `expand=workforce` |
| Flags | `1` and `0` for flags such as `is_working` and `is_decision_maker` | Booleans |

The [value translations](/docs/migrate-from-coresignal-field-mapping#value-translations) list every value.

### IDs

Coresignal IDs and CompanyEnrich IDs are separate. Coresignal company and employee IDs are integers. CompanyEnrich company IDs are UUIDs, and person IDs are 64-bit integers, so keep them in separate columns. Store the CompanyEnrich ID next to the Coresignal ID, and re-key company data on its domain.

## Verify parity on your own data

Before you move production traffic, measure CompanyEnrich on records you already have. This makes no Coresignal requests.

<Steps>
  <Step title="Check your key and plan">
    Call [`GET /v2/me`](/api-reference/v2/get-me). It is free and returns your balance and plan capabilities.
  </Step>
  <Step title="Size your searches for free">
    Send each translated query to the [company](/api-reference/v2/post-companies-search-count) or [people](/api-reference/v2/post-people-search-count) count endpoint and compare `total` with the `x-total-results` you recorded from Coresignal.
  </Step>
  <Step title="Pick a sample">
    Take 100 to 200 company records you already collected from Coresignal. Using stored records means you spend no Coresignal credits. CompanyEnrich charges 1 credit per company found.
  </Step>
  <Step title="Compare the fields you read">
    Run the script below on the sample. It enriches the domains in batches of 50 and sorts each field into `equal`, `differ`, `only Coresignal`, `only CompanyEnrich`, or `both empty`. Fields marked `lossy` in the [field mapping](/docs/migrate-from-coresignal-field-mapping) differ by definition, so leave them out or compare them by hand.
  </Step>
  <Step title="Check searches and people">
    For each translated search, run the count, then a [preview](/api-reference/v2/post-companies-search-preview) if your plan includes it, then one page. For person lookups, test work emails you already know.
  </Step>
</Steps>

<Accordion title="compare.py" icon="code">

```python compare.py
"""compare.py: compare stored Coresignal company records with CompanyEnrich on the same domains.

Usage: python compare.py coresignal_companies.jsonl   (one stored Multi-source company record per line)
Costs 1 CompanyEnrich credit per company found. Makes no Coresignal requests.
"""

import json
import sys
from collections import Counter

from companyenrich import CompanyEnrich

TYPES = {"Privately Held": "private", "Public Company": "public", "Nonprofit": "nonprofit",
         "Educational": "educational", "Government Agency": "government",
         "Self-Employed": "self-employed", "Self-Owned": "self-owned", "Partnership": "partnership"}

# Coresignal's documentation and specification spell the LinkedIn URL differently; read whichever is stored.
LINKEDIN = ("canonical_professional_network_url", "professional_network_url", "canonical_linkedin_url", "linkedin_url")


def first(record, keys):
    return next((record[key] for key in keys if record.get(key)), None)


def year(value):
    return int(value) if str(value).isdigit() else None


def place(company, part):
    return ((company.get("location") or {}).get(part) or {})


# Field -> (read the Coresignal value, read the comparable CompanyEnrich value)
FIELDS = {
    "company_name": (lambda r: r.get("company_name"), lambda c: c.get("name")),
    "website_domain": (lambda r: r.get("website_domain"), lambda c: c.get("domain")),
    "founded_year": (lambda r: year(r.get("founded_year")), lambda c: c.get("foundedYear")),
    "type": (lambda r: TYPES.get(r.get("type"), r.get("type")), lambda c: c.get("type")),
    "hq_country_iso2": (lambda r: r.get("hq_country_iso2"), lambda c: place(c, "country").get("code")),
    "hq_state": (lambda r: r.get("hq_state"), lambda c: place(c, "state").get("name")),
    "linkedin url": (lambda r: first(r, LINKEDIN), lambda c: (c.get("socials") or {}).get("linkedinUrl")),
}


def normalize(value):
    if isinstance(value, str):
        value = value.lower().removeprefix("https://").removeprefix("http://").removeprefix("www.").rstrip("/")
    return value or None


def outcome(coresignal, ce):
    if coresignal is None and ce is None:
        return "both empty"
    if ce is None:
        return "only Coresignal"
    if coresignal is None:
        return "only CompanyEnrich"
    return "equal" if coresignal == ce else "differ"


def main(path, client=None):
    records = [json.loads(line) for line in open(path) if line.strip()]
    records = [record for record in records if record.get("website_domain")]
    client = client or CompanyEnrich()  # reads COMPANYENRICH_API_KEY
    results = Counter()
    for start in range(0, len(records), 50):
        chunk = records[start:start + 50]
        batch = client.companies.enrich_batch([record["website_domain"] for record in chunk])
        for record, item in zip(chunk, batch["items"], strict=True):
            if item["status"] != "found":
                results[f"lookup: {item['status']}"] += 1
                continue
            for field, (read_coresignal, read_ce) in FIELDS.items():
                value = normalize(read_coresignal(record))
                results[f"{field}: {outcome(value, normalize(read_ce(item['company'])))}"] += 1
    for key, count in sorted(results.items()):
        print(f"{key:45} {count}")
    return results


if __name__ == "__main__":
    main(sys.argv[1])
```

## Cut over

* Put the CompanyEnrich path behind a feature flag and keep Coresignal as the fallback until the parity results meet the thresholds you set.
* Store CompanyEnrich IDs next to Coresignal IDs.
* Log `x-credit-cost` per call while both paths run.
* Move reads first, then writes to stored records, then remove the Coresignal calls, keys, and MCP configuration you no longer use.

## When to keep Coresignal

Keep Coresignal, or another source, for these workloads:

* Collect calls on stored Coresignal IDs, and employee enrichment by profile URL or shorthand name.
* Real-time employee profile scrapes.
* Job postings, company and employee posts, and webhooks for profile or experience changes.
* Company sections such as web traffic, employee and product reviews, salaries, news, key executives, competitors, acquisitions, and parent companies.
* Employee fields such as skills, certifications, salary estimates, GitHub data, and social activity.
* Searches that need OR across fields, sorting, fuzzy or wildcard matching, location text, SIC codes, skills, or job postings.
* Flat-file datasets delivered to cloud storage, and agentic search that returns a generated Elasticsearch query.

People searches support state and city IDs, but inclusion filters match only people whose reported location has been resolved to those places. Check coverage before replacing a location-based search. See [People search patterns](/docs/migrate-from-coresignal-search#people-search-patterns).

A [coding agent](/docs/migrate-from-coresignal-agent) reports searches that need OR across fields, sorting, or an unsupported clause as needs redesign: they stay on Coresignal until you decide how to change them. You can run both APIs side by side and route each call by the [endpoint mapping](#endpoint-mapping).

## Common questions

<AccordionGroup>
  <Accordion title="Can I keep using my Coresignal IDs?">
    No. Store the CompanyEnrich ID alongside the Coresignal ID, and re-key company data on its domain.
  </Accordion>
  <Accordion title="Do I still need a collect step after a search?">
    No. CompanyEnrich search results are full records. Request the expansions your code reads in the search itself.
  </Accordion>
  <Accordion title="Can I enrich a person by profile URL?">
    No. CompanyEnrich enriches a person by work email with [`POST /v2/people/enrich`](/api-reference/v2/post-people-enrich), and people search returns full records. Keep Coresignal for profile URL lookups.
  </Accordion>
  <Accordion title="Can I send Elasticsearch DSL queries?">
    No. Translate each clause to a filter with the [search patterns](/docs/migrate-from-coresignal-search). Queries that need OR across fields or sorting need a redesign.
  </Accordion>
  <Accordion title="How do I get the total number of results?">
    Send the same filter to the free count endpoint. Search responses do not include a total.
  </Accordion>
  <Accordion title="Are there webhooks?">
    No. Re-enrich the companies you follow on a schedule and compare `updatedAt`, headcount, or funding, or re-run a search and compare IDs.
  </Accordion>
  <Accordion title="Do batch and bulk enrichment need a specific plan?">
    No. Batch and bulk enrichment work on every plan.
  </Accordion>
</AccordionGroup>
